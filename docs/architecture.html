diagram-layout-demos

十二个参考图示场景走同一条流水线：布局外包给 Graphviz 与 D2，质量交给三道写死的像素阈值。这一页讲清楚这条流水线上有哪些东西、谁在哪一步把关。

2026-08-29 commit 2b30c21 draft Python 3.12+

01 · 它把自动布局当成一种渲染能力来展示

diagram-layout-demos 是一个参考图库，不是一个绘图库。仓库里没有任何布局算法：十二份图源用两种 DSL 写成（DSL 就是用文本描述一张图的领域语言），其中六份交给 Graphviz 的三种布局程序，六份交给 D2；scripts/render.py 这个 Python 脚本负责把它们逐一编译成 SVG（矢量图），再栅格化成透明底的 PNG（把矢量转成像素图），供 README 的画廊直接引用。

它给要挑布局引擎的人用。想知道「集群拓扑用 dot 画出来什么样」「放射状本体用 twopi 长什么样」「时序图交给 D2 省多少事」，打开 README 就能看到十二张由同一条流水线产出的成品图，按图示家族对照着看。

它和手画图的区别在质量闸门：每张 PNG 都要过三道像素阈值才算产出，任何一道不过线，整次运行立刻退出。代价是它只认这十二个场景——加一个场景要同时改目录、加图源、再在渲染器里登记一次。

01 · 文件名里的 transparent产物叫 *-transparent.png 不是描述，是验收对象：渲染器用 Pillow 逐像素检查透明通道，透明面积不足 5% 的 PNG 过不了关。README 表格里嵌的就是这批文件。

02 · 八件它替你做的事

  • 十二个参考场景：覆盖集群图、自由图、时序、状态机、数据谱系、构建 DAG、决策树、事件风暴等十二种图示家族；想比较布局效果时按家族挑着看。
  • 双引擎自动布局：Graphviz 负责结构化拓扑（dot / neato / twopi 三种布局），D2 负责语义化图示（时序、容器、决策树）；按图的形状挑引擎。
  • 目录驱动：catalog.json 记下每个场景的用途、要回答的问题、图示家族与引擎标签，渲染器拿它和自己的场景清单逐一对齐。
  • 一条命令全量重渲：uv run python scripts/render.py 从头跑完十二个场景，中途任何一步失败就停下。
  • 透明底出图：rsvg-convert 按 1600px 宽把 SVG 栅格化成带透明通道的 PNG，嵌进 README 表格不压底色。
  • 像素合约自检：Pillow 读回每张 PNG，量透明面积、可见面积与彩色像素数，三项都过线才算数。
  • D2 背景契约：D2 会在画布最底垫一块背景矩形，渲染器把它剥掉；剥不到就判定输出格式变了，立即退出。
  • 机器可读报告：跑完打印每个场景的尺寸、透明占比与彩色像素数，最后汇总成一份 JSON。

这八条到此为止：读者知道有这个能力、知道谁在什么场景用它就够了。每条能力内部的实现细节，属于下一层文档的范围。

03 · 整个系统只有一个进程，布局都发生在仓库之外

渲染器是仓库里唯一的可执行逻辑，它自己不画一根线。工程师用一条命令唤起它；它把图源文本递给装在系统里的三个外部程序（Graphviz 三个布局、D2、rsvg-convert），把产出的 SVG 和 PNG 写进 out/ 目录。也就是说，这个仓库的架构重心不在「怎么画」，而在「怎么把画图这件事外包出去、再怎么验收拿回来的东西」。

六个盒子各管一件事。工程师只面对一条命令；渲染器 scripts/render.py 是仓库里唯一的进程，它读目录、拼命令、验产物；Graphviz、D2、rsvg-convert 三个盒子都在仓库边界之外，缺一个整个仓库就跑不起来；产物目录收下中间的 SVG 和最终的透明 PNG。走一遍调用路径：工程师运行渲染器 → 渲染器把 .dot 图源交给 Graphviz、把 .d2 图源交给 D2 → 拿回 SVG 后再调 rsvg-convert 转成 PNG → 写进 out/。点击图中节点会跳到讲它的段落。

一个容易混的边界：Pillow 不在这张图上——它不是外部程序，是渲染器进程里 import 进来的一个库，负责最后的像素验收，所以它属于渲染器那个盒子的内部。图上五条实线都是同步调用、一个虚线框是仓库边界；按降级阶梯删掉的是 uv（只负责唤起，不参与渲染）和 README（它只是产物的读者）。

04 · 主走查：从图源到透明图

下面这条链贯穿全系统，后面两张图分别是它的两段放大。五个环节各点名它经过的组件与它做的一件事。

  1. 选场景——渲染器读 catalog.json，把目录里的十二个 id 和自己清单里的十二个名字逐一对齐；顺序或数量对不上就退出。
  2. 预检——渲染器逐个确认五个外部程序都装在系统里，缺一个就报出名字退出，不进入渲染。
  3. 编译——对每个场景拼一条命令：dot / neato / twopi 接 .dot 图源，d2 接 .d2 图源，产出 out/场景名.svg。
  4. 定妆——D2 场景先剥掉画布底部那块背景矩形；随后 rsvg-convert 把 SVG 按 1600px 宽栅格化成透明底 PNG。
  5. 验收——Pillow 读回 PNG 量三项指标（透明面积、可见面积、彩色像素数），全部过线才打印报告；任何一道失守，运行当场终止。
这条走查的名字全站通用
「从图源到透明图」是本页选定的主线名。仓库里还没有特性级文档目录，所以暂时没有别处引用它；将来做 docs/design/ 时沿用这个名字，两层文档才对得上。

05 · 五道闸门依次把守，任何一道失守就整次退出

主走查的五个环节不是五个建议，是五道闸门：渲染器把它们按顺序排好，每一道都用「不过就退出」的方式把守。这也是这个仓库最像架构的地方——它没有运行时，只有一条必须一次走完的直线。

六个盒子就是五道闸门加一份收条。目录配对确认 catalog.json 和渲染器内部清单说的是同一组场景；引擎预检用 shutil.which 找五个可执行文件；图源编译把十二份图源各自交给该管的引擎；背景契约只对 D2 场景生效；像素合约用 Pillow 读回 PNG 量三项指标。走一遍通过路径：① 配对成功 → ② 五个程序都在 → ③ 十二份图源全部编译成 SVG → ④ D2 的背景矩形被剥掉 → ⑤ 三项阈值都过线 → 输出 JSON 报告。hover 或 ← / → 可以逐步查看。

为什么图上没有五条失败分支。五道闸门的失败动作完全一样——打印原因、退出进程——把它们画成五条边只会让读者数五次同一件事，所以这里按惯例写成一句话：任何一道失败，渲染器立刻退出，排在这个场景之后的场景一次都不会跑。图上一条实线表示「通过后进入下一道」，蓝色盒子是唯一的产出。

06 · 一个场景的旅程：三次交接，两次落盘

把主走查的第三到第五个环节拆开看，一个场景要经过三次交接：图源交给渲染器、图源文本交给引擎、SVG 交给栅格器。下图按「这一步归谁负责」分成五条横带，粒子沿着四条主线跑，帮你看清哪些东西往下走、哪一步回到渲染器手里。

五条横带就是五个负责方。最上面是仓库里的三份输入：目录、六份 .dot、六份 .d2。第二条是渲染器的准备段：场景配对只做一件事——确认目录和清单说的是同一组场景；命令拼装决定每个场景该调哪个程序、带哪些参数。第三条是三个外部程序，它们真正算出布局。第四条是 out/ 里的两类文件，SVG 先落盘、PNG 后落盘。最下面一条又是渲染器：像素合约读回 PNG 做最后验收。走一遍 D2 场景：D2 图源被读入 → 命令拼装交给 D2 → SVG 写进 out/ → 同一个渲染器把背景矩形剥掉再写回 → rsvg-convert 转成透明 PNG → 像素合约读回量三项指标。

易混点：渲染器出现两次（第二条和第五条横带）不是画重了——它确实在引擎前后各干一段活，横带表达的是「这一步归谁」，不是进程数，进程始终只有一个。四条轨道周期相同、只错开相位，跑得快慢一样，长的那条只是路更远。十条边都是实线同步调用，没有异步边。按预算删掉的是 uv 的唤起动作与 README 对 PNG 的引用，它们不在渲染这条主线上。

07 · 十二个场景怎么分给两个引擎

分法只有一条：图有明确的结构就交给 Graphviz，图先有语义再谈布局就交给 D2。集群、谱系、状态机、构建顺序这类图，节点关系本身就是全部信息，Graphviz 的三种布局正好一一对应；时序、容器、决策树、组织归属这类图，读者要先看懂「这是什么关系」，D2 用声明式的语义把这件事写在图源里。下表是 catalog.json 里十二个场景的原样清单。

场景用途图示家族引擎与布局它回答的问题
architecture服务架构集群图Graphviz dot边缘信号怎么变成科学产品
knowledge知识地图自由图Graphviz neato概念之间怎么互相引用
incident事故响应流程图D2哪些动作能把服务救回来
data-lineage数据治理谱系Graphviz dot每个分析字段源自哪里
state-machine协议设计状态机Graphviz dot失败时哪些迁移合法
radial-ontology领域建模放射层级Graphviz twopi本体怎么分叉又重新连上
build-pipeline交付工程DAGGraphviz dot哪些任务卡住多平台发布
sequence分布式追踪时序D2一次结账跨过哪些服务
platform平台架构容器架构D2租户在控制面与数据面怎么隔离
decision渲染路由决策树D2该由哪个后端产出这张图
ownership团队拓扑归属图D2谁拥有服务、数据与运营结果
event-storm领域发现事件风暴D2命令、事件、策略与读模型怎么连

Graphviz 拿走六个、D2 拿走六个，比例是刻意对半的：这个仓库想回答的问题不是「哪个引擎更好」，而是「同一类图交给谁更省事」。所以两边的场景不重复——没有一个家族同时出现在两个引擎下，读者对照时不会陷入选择题。

仓库里另有一份 docs/architecture-infographic，用 TeX 画了一张关于这条流水线的信息图（PDF、SVG、PNG 各一份）。它不在渲染器的产出台账里：渲染器只写 out/，这份 TeX 的编译命令记在旁边的 render.json 中，仓库里没有再生成它的脚本推断。

07 · 两套产物，两条来路out/ 里的十二张图由 scripts/render.py 生成，可随时重跑；docs/ 下那张信息图是单独编译的 TeX 产物，重跑渲染器不会碰它。两者讲的是同一条流水线，但来路不同。

08 · 五个已经做出的取舍

取舍换来什么代价
布局全部外包给外部引擎仓库零算法依赖，Python 侧只引 pillow 一个包缺装 dot / neato / twopi / d2 / rsvg-convert 任何一个都跑不起来
目录与渲染器各存一份场景清单跑之前就能发现两边没对齐，不会渲染到一半才发现少了场景加一个场景要同时改 catalog.json、sources/ 和渲染器清单三处
像素阈值写死在代码里不用配置文件，一条命令的产出质量可预期换一种留白很多的图型，5% / 3% / 1500 这组经验值可能误伤
产物先落盘、验收在后栅格化和验收解耦，PNG 可以直接拿去比对验收失败的 PNG 已经躺在 out/ 里，渲染器不回滚，要等下次重跑才被覆盖
D2 输出靠正则剥背景一行替换就得到透明底，不用改 D2 的主题配置D2 升级后背景矩形的写法一变，渲染器会主动退出而不是画出脏图
展开：三道像素阈值各在防什么

透明面积 ≥ 5% 防「栅格化时被垫了底色」；可见面积 ≥ 3% 防「图被渲染成一张空画布」；彩色像素 ≥ 1500 防「只剩灰色轮廓、配色丢了」。三项都从 PNG 的像素直方图里算出来，不依赖引擎自报。
